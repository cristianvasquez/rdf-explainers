RDF on a Unix pipe

Snap pieces together. Quads flow through them.

Between two commands, RDF travels as N-Quads: one line per statement, four columns, subject, predicate, object and graph. Each command is a piece. It reads quads from the piece before it and writes quads to the piece after it. It does not know what the other pieces do. So the order of the pieces is the program.

There are three kinds of piece. A FILTER passes a quad or drops it. A MAP rewrites a quad. Both look at one quad at a time. A SINK must receive the whole stream before it writes anything.

The input

One file, eleven quads

rdf read people.trig turns this file into eleven N-Quads lines. Nine statements have no graph: they are in the default graph. The two salaries are in the named graph urn:g:hr. Alice's address is a blank node: a node without a global name. The task in the first examples: publish this data without the private parts.

Rules

  
What to keep in mind when you compose

  

    
FILTERMAP
One quad in, zero or one quad out. They hold one quad at a time, so they start to write at once and use little memory. Like Array.filter and Array.map.

    
SINK
Holds the whole stream until EOF. Its result can depend on any quad, also the last one. CONSTRUCT, SELECT, canonicalize and serializers are sinks.

    
Connectors must fit
A round connector carries quads. A square one carries JSON rows (after SELECT). A pointed one carries text (after pretty or ask). The shell does not check this: a misfit fails at run time, on line 1.

    
Line order has no meaning
A set of quads has no order, and two tools can write the same quads in a different order. To compare: diff <(… | rdf canonicalize) <(… | rdf canonicalize).
